# RAG فارسی — محیط کامل ساخت، آزمون و استقرار

پیاده‌سازی کامل «راهنمای جلسه: ساخت RAG فارسی از روی PDF» با **Python + LangChain**، پایگاه داده برداری
**ChromaDB** (لوکال) و **Qdrant** (سرور)، و یک **پنل وب کاملاً فارسی و راست‌به‌چپ**.

> پیام اصلی راهنما در کل طراحی رعایت شده است: در RAG فارسی بیشتر خطاها از استخراج و پاک‌سازی متن می‌آیند،
> نه از انتخاب مدل. به همین دلیل هر مرحله جداگانه قابل مشاهده، تنظیم و سنجش است.

## ویژگی‌ها

| بخش راهنما | پیاده‌سازی در پروژه |
|---|---|
| ۳. استخراج متن | PyMuPDF (با اندازه فونت و مختصات)، pdfplumber با انتخاب خودکار بهترین `x_tolerance`، OCR با Tesseract برای صفحات اسکن‌شده یا فونت بدون ToUnicode، و DOCX/TXT/MD |
| ۴. PDFهای justify | NFKC، حذف کشیده، تشخیص و اصلاح خطوط معکوس **در سطح صفحه** با امتیاز واژگان hazm، اتصال خطوط به پاراگراف، حذف سرصفحه/پاورقی تکراری و شماره صفحه |
| ۵. اعداد و جهت متن | یکسان‌سازی ارقام فارسی/عربی، ممیز و جداکننده هزارگان، حذف کنترل‌های bidi، برگرداندن اعداد و لاتین پس از معکوس‌سازی، اصلاح «» و () قرینه‌شده |
| ۶. حروف عربی | ي/ك/ة/أ/ۀ و …، حذف اعراب و ZWJ، نیم‌فاصله با hazm؛ **همان `clean_fa` روی پرسش کاربر** |
| ۷. بخش‌بندی | «ساختار ← جمله ← بودجه توکن»: تشخیص فصل/بخش/ماده (regex + اندازه فونت + bold)، مسیر عنوان (`فصل 3 - ارزشیابی › ماده 5`) داخل متن chunk، تبصره همراه ماده، همپوشانی جمله‌ای، شکستن جمله‌های خیلی بلند، جدول‌ها به markdown. روش‌های پایه recursive و fixed هم برای مقایسه وجود دارند |
| ۸. Embedding و RAG | OpenAI، Ollama و HuggingFace (پیشوند خودکار `query:`/`passage:` برای e5)، یک collection برای هر مدل، بازیابی برداری + BM25 + ترکیب RRF، reranker اختیاری cross-encoder، پاسخ استریم‌شده با ارجاع `[n]` |
| ۹. تست chunkها | audit خودکار (توکن، واژگان، کاراکتر بد، جمله ناقص، تکراری)، بازبینی chunk کنار تصویر صفحه PDF، تولید پرسش با LLM، Hit@k و MRR برای چند پیکربندی هم‌زمان |
| ۱۰. تمرین‌ها | همه تمرین‌ها از داخل پنل قابل انجام‌اند (جدول پایین) |
| داده‌های اکسل | گزارش فروش XLSX/XLS/CSV: سطرها در SQLite برای محاسبه دقیق (پرسش ← SQL ← نتیجه) و هم‌زمان chunk و embedding برای جستجوی معنایی |

## شروع سریع (لوکال، ویندوز یا لینوکس)

پیش‌نیاز: Python 3.10 یا جدیدتر.

```bash
python -m venv .venv
# ویندوز:  .venv\Scripts\activate      لینوکس/مک:  source .venv/bin/activate
pip install -r requirements.txt
# اختیاری — مدل‌های لوکال HuggingFace (embedding، LLM کوچک، reranker):
pip install -r requirements-hf.txt

cp .env.example .env          # ویندوز: copy .env.example .env
# OPENAI_API_KEY را در .env بنویسید (یا از Ollama/HuggingFace استفاده کنید)

python -m app                 # http://127.0.0.1:8000
```

سپس در پنل: **پایگاه‌های دانش ← پایگاه دانش جدید ← بارگذاری PDF ← گفتگو با اسناد**.
یک PDF نمونه با مشکلات رایج فارسی در `sample_data/` هست (با `python scripts/make_sample_pdf.py` بازسازی می‌شود).

### انتخاب مدل‌ها

| | Embedding | LLM | راه‌اندازی |
|---|---|---|---|
| OpenAI | `text-embedding-3-small` / `-large` | `gpt-4o-mini` یا جدیدتر | `OPENAI_API_KEY` در `.env` (سرویس‌های سازگار با `OPENAI_BASE_URL`) |
| Ollama | `bge-m3` | `qwen2.5:7b`، `llama3.1:8b`، `gemma2:9b` | `ollama pull bge-m3` و `ollama pull qwen2.5:7b` |
| HuggingFace | `BAAI/bge-m3`، `intfloat/multilingual-e5-large` | مدل‌های کوچک مثل `Qwen/Qwen2.5-1.5B-Instruct` | `pip install -r requirements-hf.txt`؛ مدل در اولین استفاده دانلود می‌شود |

- مدل embedding هر پایگاه دانش هنگام ساخت ثابت می‌شود؛ برای مقایسه مدل‌ها چند پایگاه دانش بسازید.
- برای e5 سقف chunk را زیر ۴۵۰ توکن نگه دارید (پنل هشدار می‌دهد).
- reranker: `RERANKER_MODEL=BAAI/bge-reranker-v2-m3` در `.env`.
- OCR: Tesseract را با زبان `fas` نصب کنید (ویندوز: نصب‌کننده UB-Mannheim و تنظیم `TESSERACT_CMD`؛ لینوکس: `apt install tesseract-ocr tesseract-ocr-fas`).

| **آزمایشگاه متن** | خروجی `clean_fa` گام‌به‌گام، مقایسه PyMuPDF/pdfplumber/OCR روی یک صفحه کنار تصویر آن، پیش‌نمایش chunkبندی بدون embedding |
| **وضعیت سیستم** | اتصال OpenAI/Ollama/HuggingFace، Chroma/Qdrant، OCR، Rerank، Jev و کارهای پس‌زمینه |
| **راهنما** | نمودار جریان همه اجزا (معماری، ایندکس‌سازی، clean_fa، پرسش و پاسخ، ارزیابی، استقرار) و توضیح همه ابزارها |

### مرحله پس از بازیابی: Rerank و Jev

هر دو روی ۲۰ کاندید بازیابی کار می‌کنند. در صفحه گفتگو (کارت «مرحله پس از بازیابی»)، آزمون بازیابی و ارزیابی روشن یا خاموش می‌شوند:

| | کار | تنظیم |
|---|---|---|
| Rerank با LLM | امتیاز ۰ تا ۱۰ برای همه کاندیدها در یک فراخوانی؛ فقط ترتیب را عوض می‌کند | `RERANK_LLM_PROVIDER`، `RERANK_LLM_MODEL` (پیش‌فرض: مدل گفتگو) |
| Rerank با Cross-encoder | مدل لوکال روی جفت (پرسش، متن) | `RERANKER_MODEL` |
| Jev (TypeSafe AI) | احتمال کالیبره «این متن واقعاً پاسخ می‌دهد»: مرتب‌سازی و حذف زیر آستانه؛ سپس بررسی «شواهد کافی است؟» و در صورت منفی، پاسخ «در اسناد موجود نیست» بدون فراخوانی LLM | `TYPESAFE_API_KEY`، `JEV_THRESHOLD`، `JEV_ANSWERABLE_THRESHOLD` |

زیر هر پاسخ نوار مراحل (بازیابی ← Rerank ← Jev ← پاسخ‌پذیری) با تعداد متن‌های حذف‌شده نمایش داده می‌شود.

ارقام فارسی در نمایش و تم روشن/تیره از نوار کناری قابل تنظیم‌اند. تاریخچه گفتگوی هر پایگاه دانش در همان مرورگر ذخیره می‌شود.

### داده‌های اکسل فروش (پرسش‌های آماری)

فایل اکسل گزارش فروش (مثل «گزارش فروش تامین‌کننده به تفکیک شعبه») را مثل هر سند دیگری در پایگاه دانش بارگذاری کنید.
فرمت‌های `.xlsx`، `.xlsm`، `.xls` و `.csv` پشتیبانی می‌شوند و دو چیدمان شناخته می‌شود (در یک فایل هم می‌توانند کنار هم باشند):

- **گزارشی:** سطرهای «تامین کننده : گل پخش اول 11572» و «شعبه : شعبه مگامال» بالای هر جدول، سطر عنوان
  (`[ردیف] [بارکد_کالا] [نام_کالا] [مقدار_فروش_رفته] [مبلغ_فروش_رفته] [مبلغ_تخفیف_سهم_تامین_کننده]`)، سطرهای کالا و سطر «جمع». چند شعبه پشت سر هم در یک شیت یا هر شعبه در یک شیت.
- **تخت:** یک سطر عنوان که ستون‌های «شعبه» و «تامین کننده» را هم دارد.

نام ستون‌ها با واژه‌های کلیدی تشخیص داده می‌شوند (تعداد/مقدار، مبلغ، تخفیف، بارکد، کالا، شعبه، تامین‌کننده). ستون‌های
دیگر هم نگه داشته می‌شوند. جمع هر ستون با سطر «جمع» خود فایل مقایسه می‌شود و اگر یکی نباشند، در جزئیات سند هشدار ثبت می‌شود.

**چرا SQL؟** بازیابی معنایی فقط چند chunk به LLM می‌دهد. پاسخ «جمع فروش شعبه X» یا «پرفروش‌ترین کالا» به همه سطرها نیاز دارد
و جمع بستن صدها عدد هم کار LLM نیست. پس در گفتگو:

1. LLM پرسش (و پرسش‌های پیگیری با توجه به گفتگو) را به یک کوئری SQLite روی جدول `sales` تبدیل می‌کند. فهرست شعبه‌ها،
   تامین‌کننده‌ها و کالاهای مرتبط با پرسش در پرامپت هست تا املای نام‌ها درست باشد.
2. کوئری روی یک کپی **درون‌حافظه‌ای و فقط‌خواندنی** از سطرهای همان پایگاه دانش اجرا می‌شود. نوشتن، PRAGMA، ATTACH
   و خواندن جدول‌های دیگر مسدود است. اگر کوئری خطا بدهد یا نتیجه‌اش خالی باشد، با بازخورد اصلاح می‌شود (حداکثر سه تلاش).
3. LLM پاسخ فارسی را از روی جدول نتیجه می‌نویسد. همان جدول و کوئری SQL هم مستقیم و بدون واسطه LLM زیر پاسخ نمایش داده می‌شود.

اگر پرسش آماری نباشد (مثلاً «بارکد فلان کالا؟» یا پرسش درباره PDFهای همان پایگاه دانش)، همان RAG معمولی اجرا می‌شود.
برای این کار سطرهای اکسل به همراه خلاصه هر شعبه و خلاصه کل فایل به‌صورت chunk هم embedding شده‌اند.

نمونه پرسش‌ها: «تعداد فروش، مبلغ فروش و تخفیف را به تفکیک شعبه نشان بده»، «جمع تخفیف سهم گل پخش اول در شعبه مگامال؟»،
«۱۰ کالای پرفروش سافتلن در میدان صنعت از نظر تعداد»، «سهم هر شعبه از کل فروش چند درصد است؟»، «و در فرشته تهران؟».

فایل نمونه `sample_data/sales-report-sample.xlsx` با `scripts/report_pdf_to_xlsx.py` از PDF همین گزارش ساخته شده است.
اعداد PDF گرد شده‌اند، پس جمع سطرها با سطر «جمع» آن چند واحد اختلاف دارد. در فایل اکسل اصلی این اختلاف وجود ندارد.

### نسخه جدید همان سند (جلوگیری از داده تکراری)

اگر نسخه اصلاح‌شده‌ای از سندی که قبلاً بارگذاری شده دوباره بارگذاری شود و هر دو بمانند، هر سطر دو بار حساب می‌شود.
در آزمون واقعی، جمع تعداد فروش شعبه مگامال به‌جای ۱۷٬۳۰۶ برابر ۳۳٬۶۱۲ پاسخ داده شد. اصلاح‌های نسخه جدید هم با مقدار قدیمی جمع می‌شوند.

- **پیش از بارگذاری** (`POST /api/collections/{id}/documents/check`): سند هم‌نام جست‌وجو می‌شود. نام با «(1)»، «- Copy»، «_v2»، «نسخه ۲»، «اصلاح شده» یا پسوند دیگر (pdf/xlsx) هم‌نام شمرده می‌شود، ولی تاریخ و دوره در نام نه.
  یک پنجره، نسخه قبلی (تاریخ، حجم، تعداد سطر و شعبه) و خطر داده تکراری را کامل توضیح می‌دهد و کاربر تصمیم می‌گیرد.
  گزینه توصیه‌شده «حذف نسخه قبلی و بارگذاری نسخه جدید» است.
- **جایگزینی امن** (فیلد `replace` در بارگذاری): نسخه قبلی فقط پس از پردازش موفق نسخه جدید حذف می‌شود و اگر پردازش خطا بدهد، دست نمی‌خورد.
  تا پایان پردازش، محاسبه‌های SQL فقط از اسناد آماده انجام می‌شود تا دو نسخه هم‌زمان شمرده نشوند.
- **پس از پردازش:** اگر فایلی با نام دیگر ولی همان محتوا آمده باشد، سند تکراری شمرده می‌شود و همان پنجره برای حذف سند قدیمی نمایش داده می‌شود. معیار، دست‌کم ۵۰٪ سطر فروش مشترک (تامین‌کننده، شعبه، بارکد) یا بخش متن یکسان است.
  در فهرست اسناد هم نشان «نسخه تکراری» می‌ماند.

### پرسش‌های پیشنهادی هوشمند

پرسش‌های پیشنهادی در گفتگو ثابت نیستند. پیش از اولین پرسش و پس از هر پاسخ، سرور (`POST /api/chat/suggestions`) آن‌ها را از سه منبع می‌سازد:

- **داده‌های همان پایگاه دانش.** برای داده فروش: نام واقعی شعبه‌ها به ترتیب فروش، تامین‌کننده‌ها، پرفروش‌ترین کالاها و کالاهای پرفروش شعبه‌ای که کاربر درباره‌اش پرسیده. برای اسناد متنی: بخش‌ها و متن‌های مرتبط با پرسش‌های کاربر.
- **گفتگوی فعلی و نتیجه آخرین پاسخ.** مثلاً سطرهای جدول SQL، تا پیشنهادها پیگیری همان مسیر باشند: جزئی‌تر کردن، مقایسه مستقیم با شعبه هم‌رتبه، یا شاخص دیگر.
- **پرسش‌های قبلی کاربر در گفتگوهای دیگر همان پایگاه دانش.** گفتگوی جدید هم از علایق کاربر شروع می‌شود.

پرسش‌های تکراری، و پرسش‌هایی با ارجاع مبهم مثل «همین شعبه» که بدون گفتگو پاسخ‌پذیر نیستند، حذف می‌شوند.
اگر LLM در دسترس نباشد، پیشنهادها با الگو از همان داده‌ها ساخته می‌شوند، مثلاً «۵ کالای پرفروش شعبه X» برای شعبه‌ای که کاربر پرسیده.

### تمرین‌های کلاس (بخش ۱۰ راهنما) در پنل

1. **سه ابزار استخراج و `vocab_score`:** آزمایشگاه متن ← مقایسه ابزارهای استخراج.
2. **شماره صفحه هر chunk:** پیاده‌سازی شده است (`page` و `page_end`) و در همه صفحات نمایش داده می‌شود.
3. **`max_tokens` برابر ۲۰۰، ۴۰۰ و ۸۰۰:** سه پایگاه دانش با همان PDF بسازید، سپس در ارزیابی هر سه را تیک بزنید. تطبیق متنی chunk طلایی بین chunkبندی‌های مختلف خودکار است.
4. **تبصره همراه ماده:** پیش‌فرض است. تبصره عنوان جدید نمی‌سازد.
5. **پرسش با ارقام فارسی با و بدون `clean_fa`:** در ارزیابی «هر دو» را انتخاب کنید، یا در آزمون بازیابی کلید نرمال‌سازی را خاموش کنید.

جدول نتایج کلاس («بدون clean_fa + برش ثابت» در برابر «clean_fa + chunk_fa» و …) با ساختن پایگاه‌های دانش
با تنظیمات متفاوت (روش بخش‌بندی «برش ثابت» و خاموش کردن «پاک‌سازی clean_fa») و یک اجرای ارزیابی پر می‌شود.

## استقرار روی سرور (Docker + Qdrant)

```bash
cp .env.example .env            # OPENAI_API_KEY و ... را تنظیم کنید
docker compose up -d --build                        # برنامه + Qdrant
docker compose --profile ollama up -d --build       # همراه Ollama
docker compose exec ollama ollama pull bge-m3       # مدل‌های Ollama
INSTALL_HF=true docker compose up -d --build        # ایمیج همراه torch برای HuggingFace (CPU)
```

- در compose، `VECTOR_STORE=qdrant` و `QDRANT_URL=http://qdrant:6333` تنظیم شده‌اند. داده‌ها در volumeهای
  `app-data` (SQLite، فایل‌ها و کش مدل‌ها) و `qdrant-data` نگه داشته می‌شوند.
- Qdrant فقط روی `127.0.0.1:6333` منتشر می‌شود. داشبورد آن روی خود سرور در `/dashboard` در دسترس است. اگر بیرون منتشرش
  می‌کنید، `QDRANT__SERVICE__API_KEY` و `QDRANT_API_KEY` را تنظیم کنید.
- برنامه احراز هویت ندارد. روی سرور عمومی آن را پشت reverse proxy با احراز هویت (مثلاً Basic Auth در nginx) یا VPN قرار دهید.
- برای استریم پاسخ پشت nginx بافر را خاموش کنید (هدر `X-Accel-Buffering: no` هم ارسال می‌شود):

```nginx
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 600s;
    client_max_body_size 100m;
}
```

- پشتیبان‌گیری: volume `app-data` و snapshot های Qdrant (`POST /collections/{name}/snapshots`).
- برنامه با **یک worker** اجرا می‌شود، چون کارهای پس‌زمینه و کش BM25 درون همان فرایند نگه داشته می‌شوند.

### استقرار بدون Docker (مثلاً RunPod یا هر سرور Ubuntu)

pod های RunPod خودشان کانتینر هستند و Docker درونشان اجرا نمی‌شود. برای این حالت دو اسکریپت هست که
Python 3.12 (با uv)، وابستگی‌ها، torch نسخه CPU، Tesseract فارسی و باینری Qdrant را نصب و اجرا می‌کنند:

```bash
bash scripts/server_install.sh        # WITH_HF=0 برای نصب بدون torch
nano .env                             # OPENAI_API_KEY، APP_PASSWORD، HOST و PORT
bash scripts/server_start.sh          # شروع یا ری‌استارت Qdrant و برنامه؛ لاگ‌ها در logs/
bash scripts/server_start.sh stop
```

- **ورود:** روی سرور عمومی حتماً `APP_PASSWORD` را تنظیم کنید. مرورگر فرم ورود (HTTP Basic) نشان می‌دهد و نام کاربری `APP_USERNAME` است (پیش‌فرض `admin`).
- **RunPod:** فقط پورت‌هایی که در تنظیمات pod به‌عنوان HTTP Port تعریف شده‌اند از آدرس
  `https://<POD_ID>-<PORT>.proxy.runpod.net` در دسترس‌اند. `HOST=0.0.0.0` و `PORT` را برابر همان پورت بگذارید.
  برای اجرای خودکار پس از روشن شدن pod، فراخوانی `server_start.sh` را ابتدای `/post_start.sh` اضافه کنید.
  داده‌ها فقط وقتی پس از Stop باقی می‌مانند که پروژه روی Volume Disk (`/workspace` متصل) باشد.
- **خطای 429 از HuggingFace** روی IP های مشترک: `HF_TOKEN` را در `.env` بگذارید، یا پوشه مدل را از کش
  `~/.cache/huggingface/hub` سیستم دیگری به `data/hf-cache/hub` سرور کپی کنید.

## API

مستندات تعاملی در `/api/docs`. مسیرهای اصلی:

| مسیر | کار |
|---|---|
| `GET/POST /api/collections` | فهرست و ساخت پایگاه دانش |
| `POST /api/collections/{id}/documents` | بارگذاری فایل‌ها (multipart) و شروع ایندکس |
| `POST /api/search` | بازیابی بدون LLM (`mode`: dense / bm25 / hybrid) |
| `POST /api/chat` | پاسخ استریم‌شده (SSE: `sources`، `token`، `done`، `error`) |
| `GET /api/collections/{id}/audit` | audit chunkها |
| `POST /api/eval-sets/{id}/run` | اجرای ارزیابی Hit@k و MRR |
| `POST /api/lab/normalize` | `clean_fa` گام‌به‌گام |
| `GET /api/jobs/{id}` | پیشرفت کار پس‌زمینه |
